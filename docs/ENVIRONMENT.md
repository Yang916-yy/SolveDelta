# Environment and Installation

This document defines the environment expected by the current SolveDelta
package. It describes implementation support, not operator mathematics; the
FP64 recurrence remains owned by `causallsso/reference.py`.

## Supported surfaces

| Surface | Requirement | Notes |
| --- | --- | --- |
| FP64/PyTorch oracle | Base package dependencies; CPU or CUDA | Intended for correctness and small reference cases |
| Dense native training | Linux x86-64, NVIDIA CUDA GPU, BF16 | Optimized production surface |
| Projected mixer/CausalLM | FLA 0.6.0 | Uses FLA kernel internals and model components |
| Default conv4 frontend | causal-conv1d 1.7+ | Installed by the `native` extra |
| CUDA Graph training | Fixed `[B,T]`, one CUDA device per process | No masks, resets, cache, hooks, or checkpointing inside capture |

ROCm, MPS, Windows-native execution, and CPU-native acceleration are not
currently supported production surfaces. WSL2 works with a compatible NVIDIA
driver. Ampere or newer hardware is recommended because the production
precision contract uses BF16 operands and Tensor Core accumulation.

The dense CUDA path currently requires sequence lengths divisible by 16 and a
unit innermost vector stride. `r=128` is the first tuned profile, not a
mathematical requirement. Masks, resets, and irregular segments preserve the
same Residual-Frame semantics through the PyTorch reference path.

## Dependency ownership

| Dependency | Declared range | Purpose |
| --- | --- | --- |
| Python | `>=3.10` | Package and compiler host language |
| PyTorch | `>=2.7,<3` | Tensor runtime, autograd, CUDA Graphs, allocator |
| Transformers | `>=4.53.3,<6` | Configuration, auto classes, causal-LM outputs |
| flash-linear-attention | `==0.6.0` | Gated-Oja, DPLR, KDA, norm, and model primitives |
| causal-conv1d | `>=1.7,<2` | Default depthwise conv4, SiLU, final-state VJP |
| Triton | PyTorch-compatible release | Compiles SolveDelta and FLA GPU kernels |
| pytest | `>=8` | Acceptance suite only |

FLA is pinned exactly because production imports and specializes private kernel
modules rather than relying only on its public layer ABI. Upgrade it only with
the oracle, composed VJP, model, and CUDA Graph suite. A CUDA PyTorch wheel
normally installs its matching Triton release; do not independently replace
Triton without checking PyTorch compatibility.

## Install

Create an isolated environment. Install the CUDA-enabled PyTorch build selected
for the host driver using the official PyTorch installer, then install the
repository and native dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip setuptools wheel

# Use the CUDA command generated by https://pytorch.org/get-started/locally/
# before the editable install when the default index would select CPU PyTorch.
python -m pip install -e ".[native,test]"
```

Prebuilt wheels do not require a local CUDA toolkit. If causal-conv1d must
compile from source, install a compiler, `ninja`, and a CUDA toolkit compatible
with the selected PyTorch build. `MAX_JOBS=<n>` can cap build parallelism on
memory-constrained hosts.

## Verify

Confirm that PyTorch sees CUDA and that all native imports resolve:

```bash
python - <<'PY'
import torch
import triton
import transformers
import fla
import causal_conv1d

assert torch.cuda.is_available()
print("GPU:", torch.cuda.get_device_name())
print("capability:", torch.cuda.get_device_capability())
print("PyTorch/CUDA:", torch.__version__, torch.version.cuda)
print("Triton:", triton.__version__)
print("Transformers:", transformers.__version__)
print("FLA:", fla.__version__)
print("causal-conv1d:", causal_conv1d.__version__)
PY

python -m pytest -q -s
```

The first native invocation includes Triton JIT compilation and must not be
used as a latency sample. Use a persistent writable cache, optionally through
`TRITON_CACHE_DIR`, when jobs run with ephemeral home directories.


This snapshot is evidence that the listed combination works. The broader
declared ranges are compatibility bounds, not a promise of identical kernel
latency or compilation behavior.

PyTorch 2.13.0's Inductor import still eagerly defines deprecated MKLDNN
TorchScript wrappers when FLA registers its public `torch.compile` callables.
SolveDelta scopes that one known deprecation to the FLA import window; it does
not change the process-wide warning policy. PyTorch PR 189914 makes these
wrappers lazy upstream and should remove the compatibility scope from a future
stable release. Re-run the full suite with deprecations promoted to errors when
upgrading PyTorch.

## Distributed CUDA Graph training

`SolveDeltaGraphedTrainingStep(..., distributed=True)` requires PyTorch 2.13
or newer, an initialized NCCL process group, and one selected CUDA device per
process. Construct the helper before wrapping or otherwise registering module
hooks: it captures local loss forward/backward first, then installs DDP on the
captured callable. NCCL reduction, the optimizer, clipping, and gradient
accumulation remain outside the CUDA Graph. `graph_step.no_sync()` delegates to
DDP for unreduced accumulation microbatches.

Construction and replay must use the same CUDA stream. The helper retains each
parameter's gradient edge on that stream before PyTorch's private side-stream
warmup, preventing `AccumulateGrad` and DDP reducer hooks from retaining the
capture stream. This relies on PyTorch's stale-capture-stream override, which
is scoped to graph construction and restored immediately afterward.

For gradient accumulation, pass the already-constructed optimizer as
`bf16_shadow_optimizer`. The helper keeps FP32 Linear parameters as optimizer
and checkpoint owners, installs nonpersistent BF16 shadows, and refreshes them
from an optimizer post-step hook. The hook and graph replay must use the
construction stream. Parameter changes outside that optimizer deliberately
raise on the next replay until `refresh_bf16_shadow_weights()` is called. This
mode trades roughly two bytes per Linear parameter for avoiding the same cast
on every microbatch; it is not recommended for accumulation factor one.

## Common failures

- `No module named 'fla'`: install the repository again so the pinned FLA
  dependency is resolved; the distribution name is `flash-linear-attention`
  and the import name is `fla`.
- causal-conv1d build failure: verify that the compiler and CUDA toolkit match
  the installed PyTorch CUDA runtime, and install `ninja` and `packaging`.
- CPU tensors entering the native path: run the FP64/PyTorch oracle directly
  or move the dense model and inputs to one CUDA device.
- unexpected reference dispatch: omit an all-ones attention mask for dense
  batches and use a length divisible by 16.
- slow first iteration: allow Triton and causal-conv1d warmup before timing;
  use CUDA Graph replay only after capture has completed.
- CUDA Graph `AccumulateGrad` stream mismatch: use PyTorch 2.13 or newer,
  construct and replay the helper on one stream, and let `distributed=True`
  install DDP after capture rather than wrapping the model first.
- stale BF16 shadow weights: update parameters through the optimizer bound to
  the graph helper, or explicitly refresh after an out-of-band state load.
